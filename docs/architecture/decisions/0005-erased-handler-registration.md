# ADR-0005: Non-Generic (Erased) Handler Registration

**Status:** Accepted
**Date:** 2026-04-02
**Relates to:** [#58](https://github.com/all-source-os/all-frame/issues/58)

## Context

AllFrame's Router registers handlers via generic methods like `register_result_with_args<T, R, E, F, Fut>()`. Each call monomorphizes the method and the `ErasedHandler` constructor with up to 5 type parameters. For a project with ~643 handlers, this creates ~643 unique generic function instantiations.

The Rust compiler's trait solver has a finite recursion depth. When many generic instantiations coexist in one compilation unit, the cumulative trait-resolution pressure can overflow the solver on **unrelated** traits (e.g., `itertools::ChunkBy: IntoIterator`), producing the opaque `E0275` error.

### Prior mitigation (v0.1.26)

We replaced the 4 per-handler generic structs (`HandlerFn<F,Fut,R>`, etc.) with a single `ErasedHandler` type, reducing `impl Handler` blocks from N to 1. This removed the per-handler trait impl overhead but did **not** reduce the N generic function monomorphizations at registration time.

### Why v0.1.26 was insufficient

The `register_*` methods are still generic. Each call to `register_result_with_args(name, handler)` monomorphizes both the Router method and the `ErasedHandler::with_args<F,T,Fut,R>()` constructor. The compiler must verify all trait bounds (`Fn`, `Future`, `Send`, `Sync`, `DeserializeOwned`, `Serialize`, `Display`) for each unique closure type. At 643 handlers, this saturates the trait solver.

## Decision

Provide a **fully non-generic registration path** where the compiler sees only concrete types at each call site, eliminating generic monomorphization entirely.

### Architecture

```
                    Generic path (existing)          Erased path (new)
                    ========================         ========================

User code           router.register_result_          router.register_erased(
                      _with_args("name", handler)      "name",
                                                       erase_handler_with_args!(
                                                         handler, ArgsType
                                                       )
                                                     )

Monomorphization    ErasedHandler::with_args          NONE (concrete code
per call site       <F, T, Fut, R>(handler)           generated by macro)

Trait resolution    Abstract: verify F: Fn(T)->Fut,   Concrete: verify
                    T: DeserializeOwned, etc.          ArgsType: DeserializeOwned
                    for abstract type params           for one specific type

impl Handler        1 (ErasedHandler)                 1 (same ErasedHandler)
blocks total
```

### Components

1. **`ErasedHandler::from_closure(Box<HandlerCallFn>)` / `ErasedStreamHandler::from_closure()`**
   Public constructors that accept pre-boxed closures. No generics.

2. **`Router::register_erased()` / `Router::register_streaming_erased()`**
   Non-generic registration methods that accept pre-erased handlers.

3. **`erase_handler!` macro family** (8 macros)
   Declarative macros that generate the boxing/erasure code inline as concrete
   (non-generic) Rust. The compiler only checks trait impls for the specific types
   used, not for abstract type parameters.

   | Macro | Handler signature |
   |-------|-------------------|
   | `erase_handler!(handler)` | `async fn() -> R` |
   | `erase_handler_with_args!(handler, T)` | `async fn(T) -> R` |
   | `erase_handler_with_state!(handler, S, T, states)` | `async fn(State<Arc<S>>, T) -> R` |
   | `erase_handler_with_state_only!(handler, S, states)` | `async fn(State<Arc<S>>) -> R` |
   | `erase_streaming_handler!(handler)` | `async fn(StreamSender) -> R` |
   | `erase_streaming_handler_with_args!(handler, T)` | `async fn(T, StreamSender) -> R` |
   | `erase_streaming_handler_with_state!(handler, S, T, states)` | `async fn(State<Arc<S>>, T, StreamSender) -> R` |
   | `erase_streaming_handler_with_state_only!(handler, S, states)` | `async fn(State<Arc<S>>, StreamSender) -> R` |

4. **`register_handlers_erased!` batch macro**
   Registers multiple handlers in one call with a declarative syntax:
   ```rust
   register_handlers_erased!(router, {
       "health"  => health(),
       "get_user" => get_user(args: GetUserArgs),
       "update"  => update(state: AppState, args: UpdateArgs),
       "events"  => stream events(args: EventFilter),
   });
   ```

### Why declarative macros, not proc macros?

A proc macro could inspect function signatures and auto-generate erasure code.
However:

- **Proc macros can't do type resolution.** They operate on token streams, not types.
  We'd still need users to provide type names for args/state.
- **Declarative macros are simpler.** No additional dependencies, no compilation overhead,
  easy to audit.
- **The `#[allframe_handler]` attribute is orthogonal.** It validates signatures and suppresses
  dead-code warnings. Erasure is a registration concern, not a definition concern.

## Consequences

### Positive

- **No E0275 ceiling.** Projects can register thousands of handlers without hitting
  trait-resolution overflow.
- **Zero runtime cost.** The erased path produces identical code to the generic path at
  runtime (same `Box<dyn Fn>` + `Box::pin`).
- **Backward compatible.** Existing generic `register_*` methods are unchanged. The erased
  path is opt-in.
- **Incremental migration.** Projects can convert handlers one at a time.

### Negative

- **Explicit type annotations.** The erased macros require the args type and state type
  to be specified explicitly (e.g., `erase_handler_with_args!(handler, MyArgs)`), whereas
  the generic methods infer them.
- **Two registration APIs.** Users must choose between the generic path (simpler, limited
  scale) and erased path (more verbose, unlimited scale).

### Neutral

- The old generic handler structs (`HandlerFn`, `HandlerWithArgs`, etc.) are soft-deprecated
  via doc comments but remain functional for backward compatibility.

## Alternatives Considered

1. **Increase `recursion_limit`** — Fragile; any new handler or type change can re-trigger.
   Doesn't fix the root cause.

2. **Split handlers across compilation units** — Requires users to restructure their project.
   Not always feasible (e.g., Tauri plugin registration in one function).

3. **Enhance `#[allframe_handler]` proc macro to generate erasure** — Would remove the need
   for explicit type annotations, but proc macros cannot resolve types from the signature
   alone (e.g., `Result<User, MyError>` vs `String` requires knowing which `IntoHandlerResult`
   impl applies). Deferred to a future version if warranted.
